# Turbopack first-wins module factory reproduction

Reproduction for [vercel/next.js#98099](https://github.com/vercel/next.js/issues/98099).

- **Next.js:** 16.3.3 and 16.4.0-canary.12
- **Bundler:** Turbopack production build
- **Router:** Pages Router
- **Runtime:** browser

## Quick reproduction

```bash
npm install
npm run verify
```

`verify` builds the app and runs machine-checked assertions. It exits with an error if the expected evidence is missing.

The commands can also run separately:

```bash
npm run build
npm run analyze
npm run repro:natural
npm run repro:synthetic
```

No browser or dev server is required. The scripts discover chunk names and module IDs from `.next`; they do not depend on generated hashes.

To check the reported canary version:

```bash
npm install --no-save next@16.4.0-canary.12
npm run verify
```

## Natural evidence

The app has only two relevant pages and one target module:

- [`pages/dyn-a.js`](pages/dyn-a.js) imports `lib/heavy.js` dynamically.
- [`pages/dyn-b.js`](pages/dyn-b.js) imports the same module statically and dynamically.
- [`lib/heavy.js`](lib/heavy.js) is the shared target.

Turbopack emits the same async-loader module ID in both page chunks with different factories:

```text
/dyn-a: load the target chunk, then require the target module
/dyn-b: Promise.resolve, then require the target module
```

`npm run repro:natural` evaluates the real, unmodified runtime and page chunks in both orders. Assertions verify that one order requests the target chunk and the other order does not. The runtime silently keeps whichever factory registers first.

## Synthetic runtime evidence

`npm run repro:synthetic` uses the production runtime generated by this build, but sends it synthetic compressed registration tuples:

```text
group A: [100, 101] -> factory A
group B: [101, 102] -> factory B
```

Because ID `101` already has factory A, `installCompressedModuleFactories` assigns factory A to ID `102` and discards factory B. Instantiating `102` then enters the wrong merged scope and throws:

```text
Module 999999 was instantiated because it was required from module 102,
but the module factory is not available.
```

The script asserts this error and also asserts that group B succeeds without the overlap.

## Evidence boundary

This repository proves:

- A clean Next.js build emits one module ID with different loader factories.
- Registration order selects the installed behavior.
- The real runtime can discard a compressed group's factory and bind new IDs to a foreign merged scope.

This repository does not prove:

- A natural crash in this small app. Both natural orders complete successfully.
- That one clean build emits non-identical overlapping merged groups. The deterministic overlap case is synthetic.
- Which path causes the matching production failures.

## Probable code path

The likely invariant break is between async-loader code generation and module identity:

1. [`AsyncLoaderModule::chunk_item_content`](https://github.com/vercel/next.js/blob/canary/turbopack/crates/turbopack-ecmascript/src/async_chunk/module.rs#L155) changes the factory body based on whether the target chunks are already available.
2. [`AsyncLoaderModule::asset_ident_for`](https://github.com/vercel/next.js/blob/canary/turbopack/crates/turbopack-ecmascript/src/async_chunk/module.rs#L54) identifies the loader from its target module.
3. [Global module ID generation](https://github.com/vercel/next.js/blob/canary/turbopack/crates/turbopack/src/global_module_ids.rs#L27) collects that loader identity.
4. [`installCompressedModuleFactories`](https://github.com/vercel/next.js/blob/canary/turbopack/crates/turbopack-ecmascript-runtime/js/src/shared/runtime/runtime-utils.ts#L590) preserves the first registered factory.

`AsyncLoaderModule::chunk_item_content_ident` already adds availability information. The emitted output shows that this does not prevent the same numeric module ID from receiving the two different bodies. A fix can make the body availability-independent or make the emitted identity availability-specific.

Changing the runtime to prefer the last factory is not sufficient. [Next.js PR #89976](https://github.com/vercel/next.js/pull/89976) added first-factory reuse to keep existing members of a compressed group consistent.

## Production context and workaround

We see the same missing-factory error intermittently during cold loads in a large Pages Router app on iOS WKWebView. One measured build has about 3,300 chunks and 59 divergent async-loader IDs. On 9 pages, a `Promise.resolve` variant registers before its target factory, which is in another page chunk.

Our current workaround is:

```js
// next.config.mjs
experimental: {
  turbopackScopeHoisting: false,
},
```

This removes merged groups from the affected production build with a 0.4% gzip size increase. It does not remove divergent async-loader factories.
